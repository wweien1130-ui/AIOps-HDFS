# OpenClaw 与后端项目互通总结

## 目标

实现完整链路：**微信 → OpenClaw Agent → 后端 API → ClickHouse/Redis → 返回数据 → 微信回复**

- OpenClaw 运行在 WSL Ubuntu（端口 18789）
- FastAPI 后端运行在 Windows（端口 8000）
- ClickHouse/Redis/Kafka 运行在虚拟机（192.168.115.129）
- 微信通过 OpenClaw WeChat Plugin 接入

---

## 尝试过的方案（均失败）

### 1. HTTP API 直连

**做法**：调用 OpenClaw 的 Chat Completions HTTP API（`POST /v1/chat/completions`）

**失败原因**：OpenClaw 的 15 个内置 skill 将工具声明注入 system prompt，Agent 收到请求后尝试调用工具而非直接返回文本，始终返回空响应 `"No response from OpenClaw"`

### 2. 专用子 Agent（api-agent）

**做法**：在 `openclaw.json` 中创建独立的 `api-agent`，使用独立 workspace，限制工具使用

**失败原因**：内置 skill 的工具声明仍然被注入，Agent 行为不可控

### 3. CLI 子进程调用

**做法**：通过 `wsl bash -c 'openclaw agent --agent api-agent --message "..." --json'` 以命令行方式调用

**失败原因**：每次调用启动新进程，响应不稳定，且 WSL 子进程调用有严重的路径转义问题

### 4. MCP Server

**做法**：编写 Node.js MCP Server（`mcp_server/index.js`），定义 4 个工具（get_system_health、get_recent_anomalies、get_top_anomalies、get_event_distribution），通过 `openclaw mcp set hdfs-monitor` 注册

**失败原因**：
- `openclaw mcp set` 配置了 MCP Server，但工具不会自动暴露给 Agent
- `tools.allow: ["hdfs-monitor"]` 导致 "No callable tools remain" 错误
- MCP 工具与 Agent 的工具系统不互通

### 5. OpenClaw Skill

**做法**：在 `~/.openclaw/skills/hdfs-monitor/` 创建 `SKILL.md`

**失败原因**：Skill 显示 "✓ ready" 但不被 Agent 自动加载，只有 "openclaw-bundled" 类型的 skill 才会自动加载

---

## 最终方案：AGENTS.md + 统一端点

### 核心思路

**OpenClaw 只做消息通道，后端 Supervisor 做大脑。**

不是让 OpenClaw Agent 自己去理解意图、选择 API、分析结果，而是让它把用户的任何消息原封不动转发给后端，由后端的 LangGraph Supervisor 统一处理。

### 架构

```
微信 → OpenClaw WeChat Plugin → OpenClaw Agent（WSL）
                                      │
                                      │ exec: curl POST /api/wechat/chat
                                      ↓
                               FastAPI 后端（Windows:8000）
                                      │
                                      ↓
                               ReactAgent.execute_stream()
                                      │
                                      ↓
                               LangGraph Supervisor
                               （LLM 意图分类）
                                      │
                        ┌─────────────┼─────────────┐
                        ↓             ↓             ↓
                   Diagnosis      Data/General   Ops/Monitor
                    (云Qwen)      (云Qwen/纯Py)  (云Qwen/纯Py)
                        │             │             │
                        ↓             ↓             ↓
                   ClickHouse / Redis / Kafka / 本地工具
```

### 具体实现

#### 1. 后端：新增统一端点 `POST /api/wechat/chat`

位置：`api/main.py:240`

```python
@app.post("/api/wechat/chat")
async def wechat_chat(request: ChatRequest):
    agent = get_agent()  # ReactAgent 单例
    full_response = ""
    for chunk in agent.execute_stream(request.message):
        if chunk:
            full_response += chunk
    return {"content": full_response.strip()}
```

特点：
- 非流式，一次请求返回完整文本（适配 OpenClaw 的 curl 调用）
- 使用 ReactAgent 单例，保持跨请求的对话记忆
- 走完整 Supervisor → 子 Agent 链路

#### 2. OpenClaw：更新 AGENTS.md

位置：`/home/ubunto/.openclaw/workspace/AGENTS.md`（WSL 内）

将原来的 2 条独立 curl 指令替换为 1 条统一指令：

```
当用户有任何问题，直接将问题原文通过以下接口发给后端：
curl -s "http://172.21.64.1:8000/api/wechat/chat" \
  -X POST \
  -H "Content-Type: application/json" \
  -d '{"message": "<用户的问题>"}'

后端 Supervisor 会自动判断意图并调用对应工具处理。
```

关键点：
- `172.21.64.1` 是 WSL 访问 Windows 主机的 IP（WSL 网关地址）
- 所有意图识别和工具调用都在后端完成，OpenClaw 不需要知道具体 API

#### 3. OpenClaw 重启

AGENTS.md 只在 Agent 启动时加载，修改后必须重启 OpenClaw Gateway：

```bash
openclaw gateway restart
```

## 遇到的关键问题及解决

### 问题 1：AGENTS.md Bash heredoc 损坏

**现象**：通过 bash heredoc 写入 AGENTS.md 时，JSON 中的 `{` `}` 被 bash 解释，导致文件内容损坏

**解决**：改用 Python 脚本进行文件读写，避开 bash 转义问题

### 问题 2：Agent 将 API 错误写回 AGENTS.md

**现象**：OpenClaw Agent 在 API 调用失败后，把错误信息写入了 AGENTS.md 文件

**解决**：用 Python 脚本清理并重写 AGENTS.md 的 HDFS 部分

### 问题 3：端口 8000 僵尸进程

**现象**：旧服务器进程 PID 21932 崩溃后，端口 8000 仍被占用（TCP 栈锁定），`taskkill /F`、`wmic delete` 均无法释放

**解决**：换用端口 8002，同时更新 AGENTS.md 中的 API 地址。等下次 Windows 重启后 8000 自动释放

### 问题 4：GBK 编码错误

**现象**：uvicorn 启动时报 `UnicodeEncodeError: 'gbk' codec can't encode character '✅'`

**解决**：启动时设置环境变量 `PYTHONIOENCODING=utf-8`

### 问题 5：FastAPI body 解析失败

**现象**：`/api/openclaw/simple` 端点返回 "There was an error parsing the body"

**原因**：参数类型设为 `body: dict`，FastAPI 无法正确解析

**解决**：改为 Pydantic 模型 `SimpleChatRequest(BaseModel)`

### 问题 6：WSL curl JSON 引号问题

**现象**：从 bash（通过 MSYS/Git Bash）执行 `curl -d '{"message":"hello"}'` 时，单引号被 MSYS 路径转换干扰

**解决**：从 WSL 内部执行 curl 命令，避开 MSYS 路径转换层

### 问题 7：OpenClaw 重启后 Qwen provider cooldown

**现象**：网关重启后 Qwen 模型进入 1 分钟 cooldown 状态

**解决**：等待恢复，无需干预

## 性能分析

### 耗时拆解（以"预处理数据"为例）

```
环节                          耗时        说明
──────────────────────────────────────────────────
OpenClaw 读 AGENTS.md         ~20-30s     Qwen API 调用
OpenClaw 决定用 exec 工具      ~10-15s     Qwen API 调用
执行 curl → 后端                ~2s        网络
Supervisor LLM 意图分类         ~5.5s      Qwen API 调用
子 Agent 执行 + 工具调用        ~7.8s      Qwen API 调用
OpenClaw 格式化回复             ~10-20s    Qwen API 调用
输出到微信                      ~10-30s    逐字推送
──────────────────────────────────────────────────
总计                           ~60-100s
```

瓶颈在 OpenClaw 侧：每轮涉及 3 次独立的 Qwen API 调用（读 prompt → 决策 → 格式化），每次 10-30 秒。

## 当前能力对照

| 子 Agent | 能力 | OpenClaw 可访问 |
|----------|------|:---:|
| **Supervisor** | LLM 意图分类，路由到子 Agent | ✅ |
| **Diagnosis** | 异常检测、RAG 知识检索、模型训练 | ✅ |
| **Data** | 数据预处理、批次管理 | ✅ |
| **Monitor** | 实时监控启停/查询（纯 Python） | ✅ |
| **General** | 时间、数学计算、身份介绍 | ✅ |
| **Ops** | 系统状态（读）/ 重启、删除（写，需确认） | ✅ |

## 未来优化方向

- **模型混合**：简单任务（Supervisor、General、Monitor）用本地 Ollama 8B 模型，复杂任务（Diagnosis、Data、Ops 写操作）用云端 Qwen Max，降低费用并加速简单查询
- **Supervisor 关键词路由**：将 Supervisor 意图分类从 LLM 改为关键词匹配（MonitorAgent 已经这样做），省掉一次 LLM 调用
- **端口 8000 恢复**：重启 Windows 后释放僵尸端口
